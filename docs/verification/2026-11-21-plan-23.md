## How it was checked
Each task was built from the plan's text, then reviewed before the next one began. Reviews were by AI reviewers (a
stronger model for Task 3, the new skill and its lock). Each review that found a problem was followed by a scoped fix
and a second look.

- Task 1 (ADR 0025 and the test file): approved. Every line matched the plan; no existing assertion changed.
- Task 2 (the workflow kind in the validator): the review found that the rule against doing-word names (ending in
  `-ing`) also blocked ordinary nouns such as `string-tools` and `ring-buffer`. The rule now needs three letters before
  `ing` and has a short list of allowed nouns (`ING_NOUNS`: string, spring). Two tests were added. Running names such
  as `running-lanes` are still blocked.
- Task 3 (the `parallel-lanes` skill): three rounds. The review found that the stacked-slice push could overwrite a
  person's commit. The lane now checks that `origin/<branch>` is an ancestor before it rebases, and pushes with
  `--force-with-lease --force-if-includes origin <branch>`. A claim fast-forwards to the remote branch, and only
  "already exists", "checked out" or "used by worktree" means a row is taken; any other claim error stops the lane. A
  lane given a row by its brief or a person ends if that row is taken; only a lane with no named row takes the next one.
  The push names its branch, so it does not fail with "no upstream". The coordinator hands a stage a person must start
  to the person, and lists the row as `needs <stage> started by <who>`.
- Task 4 (stage gates and the index): approved. The lane line sits in exactly nine stage Gates, and both story-index
  copies are identical.
- Task 5 (the plan's slices): approved. Four minor items were deferred to the final fix wave (DEPENDS ON must name an
  existing earlier slice with no cycle; slice 1 runs on the part's branch; a re-plan resets slice numbers; one wording).
- Task 6 (build, verify, review for slices): the review found that a slice's evidence path
  (`plans/<KEY>/slice-<n>/review-evidence.md`) was stated in one place only. It is now in every stage that writes or
  reads it and in both reviewer agents, with a test that pins it across them.
- Task 7 (onboarding): approved. The lanes' worktrees go in git's exclude file, and the one-clone rule is added to
  `AGENTS.md` only with the person's agreement.
- Task 8 (the four lane eval cases): the review built each scaffold and probed the graders. It found they could fail a
  correct run: quoted paths and chained commands slipped past the Bash patterns, and the coordinator case depended on
  when a sub-agent's report arrived. The graders now handle quoted paths and chained commands, and the case is
  independent of report timing. A new test runs right and wrong samples through every grader.
- Task 9 (docs and version): approved. The only existing test that changed is the plugin version, approved as V1.
  One minor item was deferred: the change list does not mention the 6.1.0 bump.
- Task 10 (this record): the two tests were written first and failed for lack of the file.
- Final review (the whole branch): the lock, the slice files, the tests and every gate held. It found two protocol
  holes: a waiting row could never be resumed, because lane step 4 always removed the worktree; and a sub-agent lane
  could not start the reviewer agents, because sub-agents cannot start sub-agents. It also found smaller items: the
  workspace root is not `..` inside a lane, release did not read the slice indexes, ADR 0025 said every stage has the
  invocation switch, and several minor wording and grader gaps.
- Final fix wave: the 22 tests of `FinalReviewTest` were written first and seen failing (18 failures, 4 errors),
  then the fixes made them pass. They apply five controller rulings, listed under "For the owner": a lane resumes a
  waiting row it can check, or that the decider settles in a lane the person started (R1); a sub-agent builds only a
  delegate bundle (R2); a sub-agent lane releases with `waiting: reviewer passes at <commit>` and the coordinator
  runs the passes (R3); the push wait sits in the verify row and ends on a check in git and the review tool (R4);
  and a lane started by hand is two messages in one session (R5). Real git proves the push check, a resumed claim,
  `--no-track` and the stale-folder claim. Also in this wave: the workspace root from a lane, the slice indexes at
  release, the two stages without the invocation switch (`aidlc-onboard`, `aidlc-verify`), one wording for when a
  stacked slice starts, a second part's slice folders, DEPENDS ON naming an existing earlier slice, the push exception
  in ADR 0025, the `AGENTS.md` rewrap and the change list's 6.1.0 line. Branch-new assertions in
  `scripts/test_parallel_lanes.py` were updated where the wording changed (the first claim's `--no-track`, the Order
  clash, the done row, the invocation sentence, the coordinator's two start bullets); no assertion that exists on

## For the owner
Accept or amend ADR 0025; run the four lane cases when a key or token is available.

The decisions you gave were applied as follows. The design approval (2026-11-21). O1, the middle option done pstack's
way: every stage that has `disable-model-invocation` keeps it (`aidlc-onboard` and `aidlc-verify` have none), and so
does `parallel-lanes`; a sub-agent lane reads skill files by path.
V1: aidlc 6.1.0. E1: `GATES` unchanged. O2: the plan's rulings.

One refinement to O2 needs your attention. The plan said a sub-agent sent to a stage it may not run records
`waiting: start <stage> by <who>`. Review showed that nothing ever cleared that state. It was replaced: the sub-agent
ends without writing state and reports, and the coordinator gives the person the start words. The intent is the same:
nothing runs, and the person is told.

Five controller rulings from the final review refine the approved design. Please confirm or amend each:
- R1 Resume. A lane resumes a waiting row when the decision it waits for can be checked where the stage says (a plan
  or design merged on the default branch; a pull request's approval or merge in the review tool or in git; the
  tracker), or, for a lane a person started, when the decider gives it in that session. A decision that is only a
  person's word is resumed by a lane the person starts by hand. The coordinator never relays a decision to a
  sub-agent.
- R2 Sub-agent builds only for delegate bundles. A hands-on build needs the person to confirm the restatement in the
  session, so a person starts it. This narrows O1; it removes no switch.
- R3 Reviewer passes. A sub-agent lane that reaches the reviewer passes commits the evidence file and releases with
  `waiting: reviewer passes at <commit>`. The coordinator claims the row's worktree, dispatches the reviewer agents,
  removes the worktree and starts a lane whose brief quotes their reports as data; that lane records the verdicts. A
  lane a person started runs the passes itself. The coordinator's claim of the worktree for the passes is a detail
  this wave added, because the reviewer agents read files in a working copy.
- R4 The push wait. `waiting: push and open the pull request by <who>` is written in the verify row, never in build's
  own row. It ends when `origin/<branch>` holds the branch's last commit and the pull request exists; the lane then
  writes `to do` in the verify row in place of the wait (not `done`, because the cell is verify's own), and verify
  runs next.
- R5 A lane started by hand is two messages in one session: lane mode with the row first (it claims), then the
  stage's own command.
