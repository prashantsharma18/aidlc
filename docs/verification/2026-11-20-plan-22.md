## How it was checked
Each task was built from the plan's text, then reviewed before the next one began. Reviews were by AI reviewers, and
each review that found a problem was followed by a scoped fix and a second look.

- Task 1 (ADR 0024): approved. One gap, that the ADR did not say the session writes the evidence file it is judged by,
  was carried into Task 2.
- Task 2 (evidence file and non-author verdict): the review found that the "names a commit other than the head" stop
  always fired, because the evidence and record commits sit on top of the reviewed one. It also found that the test
  evidence could come out empty without a warning: an unquoted pattern was expanded by the shell, and the diff read the
  working tree instead of HEAD. The commands now compare against HEAD with quoted patterns and `--no-renames`, so a
  deleted test always shows. The suppression marker list grew, the evidence file gained a section for a loosened check
  configuration, and a verdict is void only when code outside `plans/<KEY>/` changed, checked from any folder.
- Task 3 (recipe check, plan check): the recipe result was written to the progress note but read from the evidence
  file. It now reaches the evidence file, with the changed assertion lines and the test count at both commits. The plan
  checklist carries the plan's own fields, and the tree must be clean before the next slice.
- Task 4 (story status, release, contracts): the story-level commands read remote state without fetching first, and an
  empty or failing `git ls-remote` passed silently. They now fetch first, and an empty or missing result stops the
  release. A first publish with no `api-v*` tag is handled, tag matching is exact, and an unconfirmed row blocks.
- Task 5 (onboarding): onboarding did not say plainly that without a merge rule in the review tool every check is only
  advice. It does now, and it names who catches a deleted test, a weakened assertion or a lowered threshold.
- Task 6 (feedback): a lesson's check was not shown to fail on the mistake and pass on the fix. It must now fail in the
  old worktree with the check copied in and pass on the fixed code, and a new lint plugin or tool asks first.
- Task 7 (host-neutral words): approved. Minor items were deferred.
- Task 8 (docs): approved. Minor items were deferred to the final review. The two eval fixture files that the owner
  approved (item E1, option b) were updated.
- Task 9 (removal): approved. The 373 tests it ended with are the plan's 364 plus 9 added in fix rounds.
- Task 10 (this record): the evidence file template has nine section headings, not the eight the plan says, because
  Task 2's review added "Check configuration". The new test asserts nine.

## An incident during the fix wave
To test one commit's tree, the fix-wave implementer ran the suite with `GIT_DIR` pointing at this repository. The
eval setup scripts that `scripts/test_evals.py` runs inherited it: they ran `git init` on this repository, which set
`core.worktree`, and made a commit named `fixture` on the branch. The implementer removed `core.worktree`, reset the
branch to the commit before, and recommitted its own change. Checked afterwards: the local git config has no
`core.worktree`, `main` and the tag `checks-v1` still point at `7843f18`, no branch or tag contains the `fixture`
commit, and every commit on the branch uses the noreply identity. The cause remains: the eval harness passes a
caller's `GIT_*` variables to its setup scripts. Never run the suite with `GIT_DIR` or `GIT_WORK_TREE` set. A
follow-up should clear them in `scripts/test_evals.py` before it runs a setup script.
